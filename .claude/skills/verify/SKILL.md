# /verify —— 验收（基础档 · 读码比对）

验收回答一个问题：**实现和原型（+台账约束）之间还有什么 Gap**。v0 走基础档——读代码比对，近零成本；高级档（起环境 + 截图 + 断言重放）在 v0.2。

## 第一步：取证

运行 `node .baton/scripts/verify-collect.mjs <feature>`，卷宗里有：交接单全文、原型区块清单、台账全部拍板、载体清单（含**交接之后各载体仓的提交记录**——这就是要读的实现）、未结评论、下一个 Gap 编号。

## 第二步：读码比对（你的判断）

以**交接单的实现清单**为骨架，逐条到载体仓里读实现代码，三个维度：

1. **缺**——清单有、代码没有（或只做了一半）
2. **偏**——做了但与原型/台账拍板不一致（对照台账 D 号说，防止「定过的又改回去」）
3. **多**——代码里做了原型没有的（可能是好事，也可能是自作主张——列出来让人判断）

未结评论里研发标注过「阻塞」的项：核对是否仍阻塞。原型自身用 `check.mjs` 顺手过一遍。

## 第三步：写 Gap 报告

写 `verify/G<n>.md`（n 用卷宗里的 nextGapId）：

- 每条 Gap：**编号 · 缺/偏/多 · 对应原型区块或台账 D 号 · 实现文件位置 · 一句话说清差在哪**
- 结论行：`结果：pass`（零 Gap）或 `结果：N 处 Gap`
- 不写批评语气；Gap 是清单不是指责

## 第四步：逐条处置（AskUserQuestion）

对每条 Gap 三选一：

1. **「改实现」**——研发侧任务：把该条写清楚（文件+期望行为），留在报告里标「待改」；如果当前用户就是研发，直接帮他改
2. **「接受差异，回写原型」**——实现是对的、原型过时了：改 index.html 对应区块（沿用锚点 id）+ `ledger-append.mjs` 记一条「接受实现差异：…」（source-kind session）——**原型与实现永不分叉的关键动作**
3. **「挂起」**——标记待定，下轮验收再看

## 第五步：落档

`node .baton/scripts/verify-record.mjs <feature> --gap G<n> --result pass|gaps`
（回写的原型/台账改动会和报告一起在这一次提交里定格；不打版本标——tag 只属于交接。）

汇报：Gap 总数 · 改实现 N / 接受回写 N / 挂起 N · 状态推进到哪（pass → done）。

## 边界

- 只比对，不替研发悄悄改实现（除非当前用户就是研发本人并明确要你改）
- 载体仓不在本机（卷宗里 `exists: false`）→ 如实说「这几条无法本地核验」，别猜
- 高级档相关的 assertions.yaml / launch.recipe.yaml 只登记不执行，提到时说明「v0.2 提供重放」
