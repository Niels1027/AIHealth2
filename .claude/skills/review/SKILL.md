# /review —— 研发查待办（零 pull）

本命令是实现侧（谁跑谁就是实现方）。你可能正在自己的实现分支上、树是脏的——没关系，全程不动你的工作区。

## 流程

1. 运行 `node .baton/scripts/review-queue.mjs --json`。脚本自己做 fetch，然后**直接读远端引用的文件内容**（`git show origin/<默认分支>:<路径>`），不 checkout 不 pull。
2. 把待办讲给用户听，按功能组织：
   - 标题 + 版本 + 谁交接的
   - 交接单摘要（脚本已带 `handoffExcerpt`；用户想看全文就用 `git show origin/<branch>:<handoffDoc>` 读给他）
   - 台账摘要（脚本已带 `ledger`）：一句话讲清「此功能 N 条拍板，D3/D5 锚着你要看的区块」——让他打开页面前就知道有据可查；只报条数与标题，结论全文留给页面上的区块提示
   - @他 的未结评论（原话引用）
3. 用户想看页面 → **命令直接用脚本给的那一条**：`review-queue.mjs` 的输出里已经带了「查看：…」，它会自动判断用户装没装全局 `baton` 命令，给出他真能执行的写法（没装就是 `node .baton/scripts/open.mjs <feature> --review`）。**不要凭记忆写 `baton open`**——clone 仓库的人默认没有那个命令。
   作用：伴侣托管一个默认分支的独立 worktree（`.baton/review/`），页面永远是远端最新版，可直接点块评论——评论从那个 worktree 提交推送，照样不碰他的实现分支。
4. 用户对某条评论/实现问题想在会话里深聊 → 正常聊；他要留正式意见时，评论应留在页面上（点块），不要替他代写进 threads.jsonl——**看在 HTML、办在 session、正式意见落在页面**。

## 边界

- 本命令只读 + 引导，不做任何写操作（评论由伴侣写、实现代码是用户自己的事）
- 队列为空时直说「没有交给你的待办」，不要脑补任务
- 实现过程中发现原型有问题：引导用户在页面对应区块留评论（可 @持棒产品 或写「阻塞」标记），它会进产品的 /reply 清单——不要口头转达了事
