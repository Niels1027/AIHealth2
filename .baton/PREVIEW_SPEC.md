# 原型格式规范（PREVIEW_SPEC）

一句话定位：**preview = PRD + Figma 合一**——既是需求文档也是视觉稿，能点、能读懂逻辑、能直接照着实现。

两条判断标准，达不到就是不合格：
1. **研发不需要回来问**「这是什么意思 / 点了会怎样 / 数据从哪来」
2. **正式帧可以直接被采用**——对照现网组件即可落地，不需要设计师重画

---

## 一、整体骨架：什么时候分视图，怎么分

**单视图**（默认）：一个功能、一条链路、滚动不超过约三屏 → 不上导航，顶部放概要板块即可。

**多视图**（左侧导航栏）：出现任一情况就必须拆——
- 内容涉及**多个角色视角**（发起人看的 / 接收人看的 / 管理员看的）
- 有**独立的工程节**（算法、数据边界、接口对照）
- 单页滚动超过约三屏，混着不同主题

拆分规则：
- **一个视图 = 一个场景或一个角色的一条链路**；同一卡片的多个状态**不拆**视图（状态并排放在同一视图内）
- 导航分组顺序：**概要 → 按角色/场景分组的功能视图 → 工程组**（算法/数据/边界放最后）
- 视图命名用**业务人话**，不用内部代号（「发起人 · 统一入口」不是「模块A-v2」）

机器标记（check C10 验证对齐）：

```html
<nav data-baton-nav>
  <a data-view="overview">概要</a>
  <a data-view="initiator-entry">发起人 · 统一入口</a>
  …
</nav>
<section data-baton-view="overview">…</section>
<section data-baton-view="initiator-entry">…</section>
```

多视图时：每个视图必须在导航里、导航项必须有对应视图、必须存在 `overview` 视图且排第一。切换机制自便（hash 或 JS），标记必须齐。

## 二、概要：永远的第一屏

读者（研发、新加入的人、三个月后的自己）从这里进入。内容清单：

1. **标题 + 一句话定位**（这个功能解决什么）
2. **署名行**：版本 · 日期 · 出稿人（task.yaml 的 holder）· 状态（草稿 / 已交接 vX.Y）
3. **改动范围**：本次动了现网哪些页面/组件——carriers 的人话版（「改的是聊天页侧栏和来源卡片，不碰接口」）
4. **视图目录**（多视图时）：每个视图一行，说明看什么
5. **关键拍板**：从台账摘 3–5 条最要紧的，带 D 号
6. **阅读体例**：一句话告诉读者怎么区分正式帧和标注（见下节）

## 三、正式帧与标注严格分离

**正式帧 = 未来上线长什么样，就画什么样。** 内部零备注、零箭头、零高亮圈、零「这里将来会……」。（C8 会提示残留）

所有说明放**卡片旁边的标注区**，体例统一：

- **位置**：卡片右侧或正下方，与卡片明确隔开
- **视觉**：与正式帧强隔离——正式帧白底带阴影/边框（产品的样子），标注浅灰底、无阴影、小一号字、细边或左竖线（一看就是「说明文字」）
- **内容五维度**（按需取用，顺序固定）：
  1. 这是什么（一句话）
  2. 交互（点了/悬停/输入会发生什么）
  3. 数据来源（字段从哪个接口/表来；写死的示意数据在此声明并登记 stubs）
  4. 对应拍板（D 号，可点链到台账）
  5. 边界（为空/超长/无权限时怎样）

## 四、同一卡片的多形态：穷举并排，禁止只画理想态

一个组件的**全部状态在同一视图内并排陈列**，每个形态下方一行状态名标签。

状态穷举清单（按适用挑，但要主动过一遍）：
**空态 / 一条 / 多条 / 超长内容 / 加载中 / 错误 / 无权限 / 悬停·展开态 / 角色差异**（同一卡片不同人看到的不同）

只画数据正好、内容不长不短的理想态 = 把最难的判断留给研发现场发挥，这正是原型要消灭的。

## 五、改前 vs 改后

凡是改造现有 UI 的板块：**左「现状」右「改后」并排**。

- 现状帧要**标明来源**（截取/复刻自哪个现网文件——载体）
- **删除的东西也要展示**：标「本次移除」，让人看见少了什么，而不是靠对比记忆
- 全新页面无此要求，但要在标注里说明「现网无此页，入口挂在 X」

## 六、逻辑与算法的表达

- **分支/规则/权限/排序用表格**（行 = 情形，列 = 结果），不写大段文字
- **算法单独成节**（多视图时放工程组）：公式 + 每个变量的人话解释 + **2–3 个带真实数字的算例**（代入走一遍，让人看到输入到输出）
- **多步流程**用横向步骤图或表格，每步标注触发条件与失败去向

## 七、贴现网：基于现有 UI 改，不另起炉灶

1. **设计 token 从现网取**：颜色/字体/圆角/阴影/间距读项目的样式文件（globals.css、主题 token），新页面看起来是同一个产品
2. **控件照抄现网画法**：现网已有的按钮/卡片/胶囊/空态/表单件，沿用其视觉与交互，不发明新的
3. **新元素指明挂点**：现网没有的东西，标注里写清挂在哪个现有页面/组件的什么位置
4. 终点判断：**这套 UI 应当能被直接采用**——如果实现时研发觉得「得重新设计一遍」，原型就失败了

## 八、数据与可玩性

- 假数据要**有意义**：真实的人名、场景、语气、数量级（「张工 · 后端」不是「用户1」；金额别写 123456）
- 写死的凭证/示意数字**登记进 task.yaml 的 stubs**（C9 会拦凭证类）
- 交互真的能点：状态流转用真 JS 写出来（已有规矩，此处重申——多形态展示与可玩不冲突：静态并排陈列全部状态 + 关键链路可实际操作）
